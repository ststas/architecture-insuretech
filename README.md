# Проектная работа 8 спринта: кейс «InsureTech»

## Задание 1. Технологическая архитектура (to-be)

Схема решения: [InureTech_технологическая архитектура_to-be.drawio](Task1/InureTech_технологическая%20архитектура_to-be.drawio).

**Требования:** доступность 99,9 %, RTO 45 мин, RPO 15 мин, одинаковое время загрузки для всех регионов РФ.

**Решение (Yandex Cloud, регион** `ru-central1`**):**

- **Три зоны доступности**, в каждой по независимому зональному кластеру Kubernetes с одинаковым содержимым (раскатывает GitOps). Отказ одной зоны или ошибка деплоя в одном кластере не роняет остальные. Нагрузка делится поровну, зона загружена не больше ≈ 50 %: две оставшиеся зоны принимают весь трафик.
- **Вход пользователей:** Cloud DNS → Cloud CDN (точки присутствия во всех восьми федеральных округах) → защита от DDoS → Application Load Balancer на все три зоны.
- **Вход партнёров:** отдельно через API Gateway с лимитом 20 RPS на партнёра. Партнёрские поды вынесены на отдельную группу узлов (Bulkhead), чтобы партнёр не отнимал ресурсы у пользователей.
- **Health check:** ALB → узлы кластеров, liveness/readiness-пробы kubelet, проверка хостов БД (Patroni).
- **База данных:** Managed PostgreSQL, мастер в зоне 1, синхронная реплика в зоне 2 (RPO ≈ 0 при потере зоны), асинхронная в зоне 3, автоматический failover. Бэкапы и WAL-архив в Object Storage (PITR) обеспечивают RPO ≤ 15 мин.
- **Шардирование не применяем:** данных мало, нужны единая точка восстановления и простое переключение. Условия пересмотра указаны на схеме.
- **Мониторинг:** Yandex Monitoring с алертами.

**Ограничения, зафиксированные на схеме:** динамические запросы идут в `ru-central1`, поэтому для Дальнего Востока задержка выше (CDN выравнивает только статику). Отказ всего региона провайдера не покрывается, остаются резервные копии в Object Storage.

## Задание 2. Динамическое масштабирование контейнеров

Манифесты и лог теста: [deployment.yaml](Task2/deployment.yaml), [service.yaml](Task2/service.yaml), [hpa.yaml](Task2/hpa.yaml), [locustfile.py](Task2/locustfile.py), [hpa-scaling-log.txt](Task2/hpa-scaling-log.txt).

**Результат** (полный тест, 35 минут): Locust на 600 пользователей, 12 минут. HPA довёл реплики с 1 до 10 за ≈ 1,5 минуты, рестартов подов не было. После снятия нагрузки реплики не уменьшились (23 минуты наблюдения): память подов по метрикам Kubernetes не снижается (≈ 27Mi из 30Mi), поэтому HPA по памяти держит максимум. Сама Go-программа занимает ≈ 12 МБ, поэтому причина, вероятно, в эмуляции образа amd64 на arm64; точно не установлена. Для этого приложения лучше масштабировать по CPU или по запросам в секунду.

**Отличия от задания:**

- В Deployment добавлен `requests: 30Mi`: HPA считает утилизацию памяти от `requests`.
- В `locustfile.py` добавлен заголовок `Connection: close` и взято 600 пользователей, чтобы имитировать нагрузку как в реальной жизни. Иначе Locust держит постоянные соединения, весь трафик остаётся на первом поде, и HPA останавливается на 2 репликах.
- Образ собран только под amd64. На Apple Silicon он загружен в узел Minikube вручную (с `--platform linux/amd64`), в Deployment добавлен `imagePullPolicy: IfNotPresent`.

**Ограничение:** тест выполнен на Mac с Apple Silicon, образ amd64 шёл через эмуляцию. Метрики Go-программы показывают, что сама она занимает ≈ 12 МБ, а Kubernetes видит у пода 27Mi. На обычной amd64-машине утилизация памяти, скорее всего, будет ниже, поэтому число реплик под той же нагрузкой и поведение после её снятия могут отличаться.

## Задание 3. Event-Driven архитектура

Проблемы и риски: [problems-and-risks.md](Task3/problems-and-risks.md).

Обновлённая диаграмма: [InsureTech*C4*сontainer-diagram.drawio](Task3/InsureTech_C4_%D1%81ontainer-diagram.drawio), [PNG](Task3/InsureTech_C4_%D1%81ontainer-diagram.drawio.png).

**Главный риск:** синхронная цепочка «сервис → ins-product-aggregator → все страховые» и опрос по расписанию. С ростом числа страховых с 5 до 10 вероятность сбоя запроса почти удваивается, данные устаревают до 15 минут (core-app) и до суток (ins-comp-settlement), а ежедневная выгрузка нагружает core-app.

**Решение:** Apache Kafka (Yandex Managed Service for Apache Kafka).

- **На события переведено:**
  - `product-tariff-updated`: aggregator опрашивает каждую страховую независимо и публикует изменения продуктов и тарифов, core-app и ins-comp-settlement подписаны и обновляют свои реплики. Топик compacted, поэтому новый потребитель получает актуальное состояние.
  - `policy-issued`: core-app публикует оформленные страховки, ins-comp-settlement накапливает их у себя вместо ежедневной выгрузки по REST.
- **Остались синхронными:** веб ↔ core-app, веб ↔ client-info, core-app ↔ client-info и партнёры → core-app (нужен ответ сразу), core-app → платёжный сервис и ins-comp-settlement → страховые (внешние системы).
- **Transactional Outbox для core-app:** заявка и событие пишутся в `core-db` одной транзакцией (таблица `outbox`), публикатор внутри core-app отправляет их в Kafka. Debezium как публикатор отложен: объём событий небольшой, а встроенная задача не требует настройки логической репликации при failover БД. Для aggregator Outbox не нужен: у него нет своей БД, а повторная публикация тарифов безопасна.
- **Надёжность:** потребители идемпотентны (по id события), мониторинг отставания потребителей.
- **DLQ:** событие, которое потребитель не смог обработать после нескольких повторов, он публикует в отдельный топик `*.dlq` (по одному на основной топик) и продолжает читать дальше, поэтому одно проблемное событие не блокирует поток и не теряется. Рост DLQ виден в мониторинге, дежурный инженер разбирает причину и возвращает исправленные события в основной топик.

Декомпозиция функциональности между сервисами не менялась.

## Задание 4. Проектирование продажи ОСАГО

Схема: [InsureTech*C4*сontainer-diagram.drawio](Task4/InsureTech_C4_%D1%81ontainer-diagram.drawio), [PNG](Task4/InsureTech_C4_%D1%81ontainer-diagram.drawio.png).

**Нагрузка (допущение):** до 2 500 одновременных заявок × до 10 страховых = 25 000 пар «заявка — страховая». При опросе раз в 3–5 секунд это 5–8 тысяч запросов в секунду к страховым суммарно, реальные лимиты страховых неизвестны.

- **Хранилище osago-aggregator:** своё, PostgreSQL (`osago-aggregator-db`). Там задачи опроса (заявка, страховая, число попыток, время следующего опроса, крайний срок 60 с) и таблица `outbox`. Состояние не хранится в памяти сервиса, поэтому любой экземпляр подхватывает задачи, а перезапуск не теряет заявки.
- **Интеграция core-app ↔ osago-aggregator:** Kafka, как для тарифов. core-app публикует `osago-application-created` (через Outbox), aggregator публикует `osago-offer-received` по каждой страховой (предложение, отказ или «не ответила за 60 с»). Отдельного REST-API у aggregator для core-app нет, его контракт это сообщения.
- **API core-app для веб-приложения:** `POST /osago/applications` (ответ `202` с id заявки), `GET /osago/applications/{id}/offers/stream` (поток предложений) и `GET /osago/applications/{id}/offers` (состояние при перезагрузке страницы).
- **Веб ↔ core-app:** REST для создания заявки и **SSE** для предложений, чтобы каждое появлялось на экране сразу. Это новая зелёная стрелка на схеме. SSE проще WebSocket: нужна только передача с сервера, браузер сам переподключается.
- **Паттерны отказоустойчивости** (значки на схеме):
  - osago-aggregator → страховые: **Timeout** (на запрос и 60 секунд на заявку), **Retry** с растущими паузами (опрос), **Circuit Breaker** и **Rate Limiter** отдельно на каждую страховую. Circuit Breaker нужен, чтобы упавшая страховая не заставляла клиента ждать 60 секунд.
  - веб → core-app: **Rate Limiter** на создание заявок, **Timeout** на поток SSE.
  - потребители Kafka: **Retry** и DLQ.
- **Несколько экземпляров:** решение от этого зависит. Состояние опроса лежит в БД, лимит запросов к страховой делится на число экземпляров, Circuit Breaker у каждого экземпляра свой. Поток SSE живёт на одном экземпляре core-app, поэтому у каждого экземпляра своя группа потребителей Kafka, получающая все предложения, а при переподключении недостающее читается из БД. Потребители идемпотентны, число партиций не меньше числа экземпляров.

## Задание 5. GraphQL API для client-info

Схема: [schema.graphql](Task5/schema.graphql), примеры запросов: [queries.graphql](Task5/queries.graphql).

REST-контракт содержит три метода `GET` по id клиента: клиент, документы и родственники. Схема эквивалентна контракту и не дублирует ресурсы:

- Один запрос `client(id: ID!)`, документы и родственники вынесены во вложенные поля `Client.documents` и `Client.relatives`. Потребитель сам выбирает поля, поэтому трёх REST-вызовов и «одного огромного ресурса» больше не нужно.
- Типы `Client`, `Document` и `Relative` содержат поля REST-контракта. Все поля, кроме `id`, необязательные, потому что в Swagger нет `required`. Списки возвращаются непустыми (пустой список вместо `null`).
- Даты выделены в скаляр `Date` (ISO 8601). Тип документа и степень родства остались строками: допустимые значения в контракте не перечислены.
- Схема собирается библиотекой GraphQL, примеры запросов проходят проверку и выполняются на пробных данных. Новые данные клиента (контакты, адреса и другие) добавляются новыми полями и типами без новых ресурсов.
