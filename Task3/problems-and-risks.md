# Проблемы и риски текущей архитектуры InsureTech при росте нагрузки

## Контекст

Сервисы core-app и ins-comp-settlement получают данные о страховых продуктах и тарифах через REST API сервиса ins-product-aggregator. В момент вызова aggregator синхронно запрашивает данные у всех страховых компаний (сейчас их пять), собирает их в единый список и возвращает в том же запросе. Чтобы ускорить работу, core-app и ins-comp-settlement хранят у себя локальные реплики продуктов и тарифов:

- core-app запрашивает aggregator раз в 15 минут;
- ins-comp-settlement запрашивает aggregator раз в сутки, ночью;
- ins-comp-settlement раз в сутки забирает у core-app по REST все страховки, оформленные за день;
- раз в месяц ins-comp-settlement отправляет страховым данные для взаиморасчётов.

Уже сейчас команда сталкивается с ошибками взаимодействия из-за задержек и сбоев API страховых компаний. Компания планирует подписать соглашения ещё с пятью страховыми, то есть довести число интеграций с 5 до 10, и провести рекламную кампанию, после которой нагрузка вырастет.

## 1. Синхронная агрегация в ins-product-aggregator

- **Время ответа равно времени самой медленной страховой.** Один медленный API задерживает весь ответ, а таймаут или ошибка одной страховой ломает запрос целиком, если частичные ответы не поддержаны.
- **Вероятность сбоя растёт с числом страховых.** При 1 % отказов на каждую страховую хотя бы одна из пяти откажет примерно в 4,9 % запросов, из десяти примерно в 9,6 %. Количество проблемных запросов почти удвоится после подключения новых компаний.
- **Нагрузка умножается.** Каждый вызов превращается в 5–10 внешних запросов. Рост числа обращений к aggregator напрямую увеличивает нагрузку на API страховых, а у них могут быть лимиты и недоступные окна.
- **Разные протоколы** (REST, SOAP, GraphQL) обслуживаются в одном синхронном пути, и медленный адаптер блокирует остальные.

## 2. Опрос по расписанию и локальные реплики данных

- **Устаревшие данные.** Тарифы в core-app могут отставать до 15 минут, в ins-comp-settlement до суток. Клиент может оформить страховку по тарифу, который уже изменился.
- **Расхождение между сервисами.** Два сервиса опрашивают aggregator независимо, и в один момент у них могут быть разные версии тарифов: продали по одним, посчитали взаиморасчёты по другим.
- **Лишняя нагрузка.** Большинство опросов возвращают те же данные. При нескольких экземплярах core-app опрашивают все реплики одновременно.
- **Дублирование данных** в двух БД и двух механизмах синхронизации, которые нужно поддерживать и отлаживать отдельно.

## 3. Суточная выгрузка ins-comp-settlement → core-app

- **Нагрузка на монолит.** Запрос «все оформленные за день» читает большой объём из БД core-app, и с ростом числа клиентов выборка растёт вместе с ним.
- **Жёсткая связность по времени.** Расчёт возможен только когда одновременно доступны и core-app, и aggregator.
- **Хрупкость пакетной обработки.** Сбой посреди выгрузки приводит к повторному запуску с начала, без гарантий от потери или дублей.
- **Поздний сигнал о проблемах.** Данные о полисах попадают в расчёт раз в сутки, ошибки видны только на следующий день.

## 4. Общие архитектурные риски

- **Каскадные отказы.** ins-comp-settlement синхронно зависит от двух сервисов сразу. Сбой любого блокирует расчёты.
- **Нет гарантий доставки.** Нет повторов, очереди недоставленных сообщений и идемпотентности: при сбое непонятно, что обработано, а что потеряно.
- **Нет наблюдаемости.** Не измеряются свежесть данных и отставание реплик, о проблемах узнаём по ошибкам.
- **Масштабирование интеграций.** Подключение пяти новых страховых требует правок и роста нагрузки в той же синхронной цепочке.
- **Риск потери события при оформлении.** Если попытаться просто «отправить сообщение» после записи заявки, возможна ситуация, когда заявка записана, а сообщение потеряно (или наоборот): нужны транзакционные гарантии.
- **Монолит core-app как узкое место.** Он обслуживает пользователей, партнёров и пакетные выгрузки одновременно, и рост любого вида нагрузки влияет на остальные.

## Вывод

Основной источник риска — синхронная цепочка «клиент сервиса → aggregator → все страховые компании» и опрос по расписанию. С ростом числа страховых и пользователей вероятность ошибок и устаревших данных растёт, а один сбой затрагивает несколько сервисов. Решение в следующем разделе работы: перейти на событийную модель (публикация изменений тарифов и оформленных страховок в потоке событий), чтобы развязать сервисы по времени и убрать синхронный опрос всех страховых.
